# wifi_ps

演示 **WiFi 省电模式**（Power Save）—— 已关联的 station 不必一直开着接收机。

## 原理

station 告诉 AP「我要打盹了」，AP 就把发给它的数据先缓存起来，等到下一个 **DTIM beacon** 再一起送出。station 只在那个 beacon 醒来收一次，其余时间射频休眠。

**DTIM 间隔越大，唤醒次数越少、电流越低，代价是延迟越大** —— 等着的数据要多压一个周期。一个 beacon 通常是 102.4 ms。

这是**联网设备**的低功耗路径。不联网的设备走的是另一条 —— 见隔壁的 [cpu_sleep](../cpu_sleep/) 和 [cpu_deep_sleep](../cpu_deep_sleep/)。

## 涉及的接口

整个功能就一个调用：

```c
tkl_wifi_set_lp_mode(TRUE, dtim);
```

例程另外做的事只有「连上 AP」—— 因为**省电模式是关联状态的属性，没关联就无从谈起**。平台实现里第一步就是检查 station 是否处于 STA 模式，不满足直接返回失败。

## 配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `EXAMPLE_WIFI_SSID` | `your-ssid` | 要连接的 AP |
| `EXAMPLE_WIFI_PASSWORD` | `your-password` | 密码 |
| `EXAMPLE_WIFI_CONNECT_TIMEOUT_S` | 30 | 连接超时 |
| `EXAMPLE_WIFI_PS` | y | 是否开启射频省电，关掉用于做对照 |
| `EXAMPLE_WIFI_PS_DTIM` | 1 | 允许睡过几个 DTIM 周期，范围 1~10 |
| CPU 睡眠档位 | 浅睡 | `none` / `light` / `deep`，见下 |

### CPU 睡眠必须一起开

**射频省电和 CPU 睡眠是两笔独立的账，要叠加。** 只开射频省电，内核仍在空闲循环里满速自旋，那部分功耗一分不省 —— 在多数片子上它还是剩余功耗的大头，结果看起来像「射频省电没用」。

实测（GD32VW553 / 嘉立创板，**整板**，DTIM=1）：

| CPU 档位 | 平均电流 |
|---|---|
| `none`（只开射频省电）| 45 mA |
| `light` | 44~45 mA |
| **`deep`** | **约 3.6 mA** |

**深睡那一档随网络环境浮动很大**：完全空闲的网络能到 2.4 mA，路由上有其它设备在收发时会升到十几 mA。3.6 mA 是一般家庭网络下的实测值，比实验室里那个最好成绩更有参考意义。

差额全在射频接收上，和固件无关。

两点值得注意：

**浅睡在这颗片子上几乎没有收益。** 看波形的**地板**比看平均值清楚：

**在 GD32VW553 上，已关联的设备根本进不了浅睡** —— 实测内核全程没停过，那 44~45 mA 里的 39 mA 就是内核全速运行的电流，不是什么「地板」。

原因是平台把 CPU 睡眠深度和系统功耗模式绑在一起：浅睡对应的系统模式字面意思就是「不做省电」，于是 WiFi 协议栈没有理由交出它对电源管理的占用，睡眠请求被一直挡在门外。深睡进入的是另一个系统模式，射频那边才会配合放手。

对照 `cpu_sleep`（把射频完全交还）的地板是 1.28 mA —— 那里内核是真睡了的。

**结论：联网设备不要指望浅睡，直接用深睡。** 这一档留给不联网的场景，以及深睡走复位路线的其它平台。

这是平台特性不是浅睡的问题：在深睡走复位路线的平台上（关联活不过来），浅睡反而是唯一可用的档位，而那些平台的浅睡通常是真正的低压睡眠，地板低得多。

**网络环境的影响比所有配置项加起来都大。** 同一份固件在繁忙网络下能比空闲时高好几倍，差额全在射频接收上 —— 波形里表现为每隔几秒一个接收档幅度的宽脉冲。所以**报低功耗数字时必须说明网络环境**，否则没有可比性。

三档的用途：

- **`none`** —— 基准。先量这一档，它到另外两档的落差就是 CPU 那部分的代价，没有这个数就没法归因
- **`light`** —— **可移植的正确选择**。保持内存、外设和 WiFi 关联，任何中断（包括 beacon）都能立刻唤醒。各平台语义一致
- **`deep`** —— 更省，但**语义因平台而异**：
  - 原地恢复型（GD32VW553）可以连 PLL 和晶振一起停掉，那是剩余电流的大头。AN150 给这个组合的官方数据是 **1.43 mA**
  - 复位型（T5AI 走的是写 flash + 主动复位）**WiFi 关联活不过来**，对联网设备等于自毁。选之前先确认你的平台是哪种

跑之前必须先填 AP：

```bash
tos.py config set EXAMPLE_WIFI_SSID=myrouter EXAMPLE_WIFI_PASSWORD=mypassword
```

## 预期输出

```
connecting to "Pico" ...
connected
wifi power save on, dtim 1 -> 0
cpu light sleep   -> 0
awake
awake
```

- `-> 0` 表示省电模式打开成功；返回负数说明该平台没实现这个接口
- 连不上会直接退出并说明原因 —— **不会带着一个失败的连接去开省电模式**，否则看起来像是省电模式坏了
- `awake` 每 5 秒一次，只是为了把「在打盹」和「挂了」区分开

## 怎么验证

**必须用电流表。** 日志证明不了射频有没有真的休眠 —— 一个全程开着接收机的设备打印出来一模一样。

**看波形的形状比看平均值有用。** 做对了应该是这样：

- **基线贴近 0** —— 深睡真的下去了，PLL 和晶振都停了
- **规律的窄尖峰** —— 每个 DTIM 醒来收 beacon，间隔 ≈ `DTIM × 102.4 ms`
- **偶尔的宽脉冲** —— 网络上有东西要收，幅度会到接收档（这颗片子约 130 mA）

平均值是这三样按时间加权的结果，其中**宽脉冲取决于网络有多吵，和你的代码无关**。基线不贴 0 才是自己的问题。

在供电回路串电流表，用 `EXAMPLE_WIFI_PS` 做对照：

```bash
tos.py config set EXAMPLE_WIFI_PS=n     # 关掉省电，量一次
tos.py config set EXAMPLE_WIFI_PS=y     # 打开，再量一次
```

差值就是省电模式的收益。再把 `EXAMPLE_WIFI_PS_DTIM` 从 1 调到 5、10，能看到电流随之下降 —— 这条曲线本身就是这个例程最有价值的输出。

**注意关掉时例程是显式调 `tkl_wifi_set_lp_mode(FALSE, 0)`，不是跳过调用。** 平台往往在接口变成 station 的那一刻就自己把省电打开了（GD32VW553 就是如此），跳过调用只会让两次测的是同一个东西。

波形上还能直接看到 beacon 节律：省电模式下电流是一串规律的尖峰（每次醒来收 beacon），间隔约等于 `DTIM 间隔 × 102.4 ms`。

## 和 CPU 睡眠的关系

两者是**叠加**的，不是二选一：

| | 省的是什么 |
|---|---|
| `wifi_ps` | 射频接收机的功耗 |
| `cpu_sleep` / `cpu_deep_sleep` | CPU 内核和时钟的功耗 |

射频进入省电模式后，CPU 在 beacon 之间也没事干，可以顺带睡下去。真正的低功耗产品两边都要做。
